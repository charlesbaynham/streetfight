# A11 — per-shot map (R5), admin shot history + notes, zip download

Own game `A11-Game` (`1936ad8e-2a2a-495f-bb1f-97c427e980b8`), teams `A11-Red` /
`A11-Blue`, players `A11-Shooter`, `A11-Target`, `A11-Bystandery`, `A11-NoFix`.

## The per-shot map (R5) showing GPS accuracy and the shooter's compass heading.

**Verdict:** WORKS

**Evidence:** `$S/shots/A11-map-h000-acc8.png`, `A11-map-h090-acc8.png`,
`A11-map-h180-acc8.png`, `A11-map-h270-acc8.png`, `A11-map-h045-acc60.png`,
`A11-map-h315-acc2000.png`, `A11-map-nohead-accnull.png`,
`A11-map-h000-acc0.png`, `A11-map-faraway.png`, `A11-queue-nofix.png`,
`A11-queue-h045-acc60.png` (whole page at 390x844).

All three quantities reach the map and are drawn, not merely printed:

- **Position.** Eight shots from five different fake fixes; each map is
  re-centred on that fix and the venue drawing moves under the dot
  (`A11-map-h000-acc8.png` sits at the Victoria St / Buckingham Gate junction,
  `A11-map-h045-acc60.png` at the Greencoat Boy, `A11-map-nohead-accnull.png`
  at the White Horse). Not a static thumbnail.
- **Accuracy is a circle to scale, *and* a number.** 8 m → 17.6 px diameter,
  60 m → 132 px, measured off the live DOM; the box is 220 px for 200 m, i.e.
  1.1 px/m, so both are exactly right. Caption reads `±8 m`, `±60 m`.
- **Heading is a cone, and it points the right way.** Read the SVG path back
  for each cardinal: 0° → apex up-screen (north), 90° → right (east), 180° →
  down (south), 270° → left (west). The map is north-up (street labels
  horizontal), so screen-up *is* north and there is no 90° error. 45° and 315°
  land correctly between. Caption `facing 090°`, zero-padded.

Degradation is correct in every edge case I could build:

- **heading null** (the case the non-blocking compass rung guarantees on the
  night): no cone, caption `no heading`, everything else drawn.
- **accuracy null**: no circle, caption `accuracy unknown`.
- **accuracy 2000 m**: circle is 4400 px but `.shotMap` is `overflow: hidden`,
  so the box just goes uniformly blue — no layout blowout, no horizontal
  scroll. Caption still says `±2000 m`.
- **no fix at all** (player who never sent a location): *"No position recorded
  for this shot"* in italics, nothing drawn. `A11-queue-nofix.png`.

### Finding: accuracy of exactly 0 draws no circle at all
**Severity:** cosmetic
**What happens:** `accuracyRadiusPx` is 0, which is falsy, so the circle is
skipped entirely — the map looks identical to the "accuracy unknown" case while
the caption says `±0 m`.
**How to reproduce:** `set_location?...&accuracy=0`, then fire.
`$S/shots/A11-map-h000-acc0.png`.
**Where:** `react-ui/src/ShotMap.js:133` (`{accuracyRadiusPx ? (`).
**Why it matters for the 19th:** essentially not at all — no browser reports 0.
Noted only because it is the one falsy-vs-null slip in an otherwise careful
null-handling job.

### Finding: a shot fired outside the venue crop shows a blank white box with no explanation
**Severity:** minor
**What happens:** a fix outside the map image (I used Kingston, ~25 km away)
renders the dot, the cone and the accuracy circle on plain white — the map
background is simply scrolled off. Nothing says "off the map"; the venue
drawing is itself mostly white with black lines, so it reads as an empty patch
of Westminster rather than as no coverage.
**How to reproduce:** `set_location?latitude=51.4130&longitude=-0.3075&accuracy=15`,
fire, open in the queue. `$S/shots/A11-map-faraway.png`.
**Where:** `react-ui/src/ShotMap.js:62` — no bounds check against
`geometry.bottomLeft` / the map extent.
**Why it matters for the 19th:** a stale or wildly wrong fix (indoors, cold
start, a player still on the train) will produce exactly this, and the admin
will read "he was standing in a blank bit" instead of "this fix is junk". The
caption's `±` figure is the only clue and it can be small on a bad-but-confident
fix.

## Admin shot history and notes on a player.

**Verdict:** WORKS WITH CAVEATS — the **notes** half works well; the **history
"on a player"** half does not exist. What ships is a global, one-at-a-time
pager, and the word "player" in this checklist line has no implementation
behind it.

**Evidence:** `$S/shots/A11-notes-typed.png`, `A11-notes-saved.png`,
`A11-notes-after-reload.png`, `A11-notes-long.png`, `A11-history-view.png`,
`A11-queue-w320.png`.

Notes (`admin_get_shot_notes` / `admin_set_shot_notes`,
`react-ui/src/ShotQueue.js:359`) behave: typing flips the button to
"Save notes", saving persists, a full page reload brings the text back
verbatim. Round-tripped `"double" 'single' & <angle>`, an em dash, a newline and
emoji 🎯👕 with no mangling (`A11-notes-typed.png` shows them rendered); a
4000-character note saved and came back whole (`A11-notes-long.png`). Notes are
editable on an already-adjudicated shot too.

### Finding: there is no per-player shot history — only a 40-deep Next/Previous pager over every shot in every game
**Severity:** major
**What happens:** the only history is `ShotQueue`'s "Show adjudicated shots"
checkbox, which appends the checked shots to the same single-shot pager. There
is no list, no filter, no search, and no link from a player anywhere to their
shots. To answer "what has happened to A11-Target tonight?" the admin taps
**Next** up to N times (I was at "Shot 5 of 40" with 40 shots in a quiet test
container) and reads each one. `admin_get_shots_info` takes only
`include_checked`; there is no endpoint keyed by user at all, and
`AdminMode.js`'s `PlayerRow` (line 346) offers rename / team / slot / delete but
no history link.
**How to reproduce:** `/admin/shots` → tick "Show adjudicated shots" → try to
find one named player's shots. `$S/shots/A11-history-view.png`.
**Where:** `react-ui/src/ShotQueue.js:628` (`ShotQueuePanel`, index-based
navigation), `backend/main.py` — no `admin_get_user_shots`;
`backend/admin_interface.py:967` `get_shots_ids(include_checked)`.
**Why it matters for the 19th:** the moment a player says "that hit was wrong"
or "I've been shot three times and only lost one HP", the admin has to find
that player's shots under time pressure on a phone. At one shot per tap with a
~1 s image load between taps, a 150-shot night makes this unusable. This is
also the exact query an appeal (R8) makes you want to run.

### Finding: the adjudicated-shot history never says *when* a shot was fired
**Severity:** major
**What happens:** the history view shows `By A11-Shooter`, the photo,
`Adjudicated: Hit on A11-Target`, the map caption and the notes box — and no
timestamp anywhere. `time_created` is already in the payload
(`ShotModel.time_created`, `backend/model.py:535`); the queue simply never
renders it. The player-facing history *does* show a time
(`formatShotTime`, `ShotHistory.js`), so the admin has strictly less
information than the players do.
**How to reproduce:** tick "Show adjudicated shots", look at any checked shot.
`$S/shots/A11-history-view.png`.
**Where:** `react-ui/src/ShotQueue.js:806` (`<em>By {shot.user.name}</em>` — the
only header line) and the `Adjudicated:` line just below it.
**Why it matters for the 19th:** an adjudication argument is almost always
about ordering — was he already out when this was taken? Two shots by the same
shooter with the same photo and the same verdict are literally
indistinguishable in this view. The fix is rendering a field that is already
being fetched.

### Finding: an unsaved note is discarded silently when you page to another shot
**Severity:** minor
**What happens:** type into the notes box, tap Next, tap Previous — the typed
text is gone, replaced by the last saved value. No warning, no prompt, and the
button that would have saved it scrolls with the rest of the page.
**How to reproduce:** type "UNSAVED DRAFT" without saving → Next → Previous.
Observed textarea reverts to the previously saved note.
`$S/shots/A11-notes-lost-draft.png`.
**Where:** `react-ui/src/ShotQueue.js:363` — the `useEffect` on `shot_id` resets
`notes` and `dirty` unconditionally.
**Why it matters for the 19th:** the notes exist to preserve the admin's
reasoning for the replay harness. Adjudicating and then paging on is the normal
motion, so the reasoning most worth keeping — the one written while thinking
about a hard shot — is the one most likely to be thrown away.

### Finding: the save button reads "Notes saved" on a shot that has never had a note
**Severity:** cosmetic
**What happens:** with an empty textarea and nothing typed, the disabled button
says "Notes saved" — asserting something that did not happen. It only means
"not dirty".
**Where:** `react-ui/src/ShotQueue.js:394`.

### Finding: the notes textarea is ~155 px wide in the queue's left column at 390 px
**Severity:** minor
**What happens:** on a phone the two `<Col>`s stay side by side, so the notes
box is about 155x100 CSS px — roughly three short lines. Typing a sentence
scrolls the first line out of view (`A11-notes-typed.png`: only the second half
of my note is visible). A 4000-character note is a wall of two-word lines
(`A11-notes-long.png`, `A11-history-view.png`). Below ~576 px the columns stack
and the box gets full width (`A11-queue-w320.png`), so the *narrowest* phones
get the better notes box.
**Where:** `react-ui/src/ShotQueue.js:800-830` (bare `<Col>`, no breakpoint) and
`ShotQueue.module.css:217` (`.notesBox textarea`).
**Why it matters for the 19th:** the admin is meant to type reasoning here
one-handed, and cannot read back what they typed.

*Incidental, probably another agent's line:* the queue page scrolls
horizontally by 11 px at 390, 360 and 320 px. The offender is the
`.showCheckedToggle` labels (`react-ui/src/ShotQueue.module.css:202`), each
`width: 100%` inside a padded Bootstrap `Row`.

## Downloading all shot images as a zip.

**Verdict:** WORKS WITH CAVEATS

**Evidence:** `$S/shots/A11-zip-button.png`, `A11-zip-during.png`,
`A11-zip-after.png`; the archives themselves at `$S/a11/dump.zip` (API,
1,646,611 bytes, 40 entries) and `$S/a11/ui_download.zip` (UI button,
1,893,348 bytes, 43 entries, `testzip()` clean); one extracted image at
`$S/a11/sample.png`.

The admin-home button works end to end: `Download shot images (zip)` triggers a
real browser download named `shot_images.zip`, 5.9 s wall clock for 43 shots
(the raw API call was 2.3 s for 40 — the rest is blob handling in the page).
Every entry is a valid PNG, and the images are properly marked up: the aiming
crosshair plus a burned-in stats box reading `Shooter: A11-Shooter / Damage: 0 /
Result: Hit A11-Target` (`$S/a11/sample.png`). So the *image* tells you who
fired and what was ruled.

### Finding: filenames cannot identify a shot — the timestamp in them is the moment of the zip, not of the shot
**Severity:** major
**What happens:** every entry is `{shooter name}_{time.time()}.png`, where
`time.time()` is read while *rendering the zip*. In my archive all 40 files
carry timestamps inside a 2-second window (`A11-Shooter_1787945802.6375282.png`
… `_1787945802.8645744.png`) — the moment I pressed the button. There is no
shot id, no target, no game and no fired-at time. Eight shots by one shooter
are eight near-identical filenames whose only ordering is DB insertion order,
and the mapping back to a shot in the queue is unrecoverable.
**How to reproduce:** `POST /api/admin_dump_images`, list the archive.
**Where:** `backend/image_processing.py:31`
(`filename = f"{name}_{time.time()}.png"`), called from
`backend/postprocess_shot_images.py:_render_shot_images`.
**Why it matters for the 19th:** this dump is the post-game artefact — the pile
of photos you go through afterwards to settle arguments and to feed the replay
harness. Filenames that encode neither *when* nor *which shot* mean the only
way back to a shot record is eyeballing the burned-in caption. `shot_model.id`
and `shot_model.time_created` are both in hand at that call site.

### Finding: one player with "/" in their name makes the whole zip download 500 for everyone
**Severity:** major
**What happens:** `set_name` stores the name unsanitised
(`backend/user_interface.py:355` — `.strip()` only), and the filename is
interpolated straight into a path. A name containing `/` produces a path with a
non-existent parent and PIL raises, taking the whole endpoint down — not just
that one image. Confirmed live: renamed my own shooter to `A11-Shooter/x`,
`POST /api/admin_dump_images` → **500** in 1.2 s; renamed back → 200. Backend
log: `FileNotFoundError: [Errno 2] No such file or directory:
'/tmp/shot_images_g_8ppzic/A11-Shooter/x_1787945868.2034075.png'`
(`$S/backend.log:382731`). The name was restored within seconds. A leading
`../` is the quieter variant: the parent *does* exist, so the render succeeds,
the file lands outside the temp cache dir, `cache_dir.glob("*.png")` never sees
it, and it is silently missing from the archive while a stray PNG is left on
the server.
**How to reproduce:** `admin_set_user_name?...&name=Bob/x` (or a player typing
it themselves at onboarding), then press the download button.
**Where:** `backend/image_processing.py:31-33`;
`backend/postprocess_shot_images.py:20-33`; no validation in
`backend/user_interface.py:355`.
**Why it matters for the 19th:** players type their own names. One person
called `Rob/Bob` or `and/or` and the post-game image dump is dead, with an
opaque 500 in the admin error box and no hint which player caused it. Also a
real (if low-value) path traversal driven by unvalidated player input.

### Finding: the download button gives no feedback at all while the zip builds
**Severity:** minor
**What happens:** the button does not disable, change label, or show a spinner;
the page is visually identical during the 6 s render
(`$S/shots/A11-zip-during.png`, taken immediately after the click, is
indistinguishable from `A11-zip-button.png`). Nothing indicates work is
happening or how much is left.
**Where:** `react-ui/src/AdminMode.js:530-539` — a bare `<button onClick=...>`;
`AdminCommon.js:23` `adminDownload` has no pending state.
**Why it matters for the 19th:** the whole zip is rendered and buffered in
server memory (`io.BytesIO` in `zip_shot_images`) and then again as a browser
blob, with no streaming and no cancel. 43 tiny synthetic shots took 6 s here on
localhost; a real night's several-hundred phone-camera photos will take long
enough over mobile data that an admin with no feedback will tap again — and
each tap starts an independent full re-render of every shot in the database.
(The re-tap amplification is inference from the code, not something I hammered
the shared server to prove.)

### Finding: the zero-shots case is not reachable on the shared container
**Severity:** question
**What happens:** the dump is system-wide (`get_all_shot_ids()` has no game
filter), and the shared database has 40+ shots from other agents, so I could
not exercise the empty case without a reset — which the brief forbids. By
inspection `zip_shot_images` would return a valid but empty archive with HTTP
200, and `adminDownload` would save a 22-byte `shot_images.zip` with no message
distinguishing it from a failure.
**Where:** `backend/postprocess_shot_images.py:52-68`.
**Why it matters for the 19th:** minor, but "I pressed it and got an empty
file" is indistinguishable from "it silently broke".
