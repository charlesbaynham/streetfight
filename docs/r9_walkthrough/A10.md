Game: `A10-Game` = `fdc1eb2f-04ac-4ad8-9278-d7266c28a7ab`, teams `A10-Red` / `A10-Blue`,
players A10-Alice (purple/grey/purple/purple), A10-Bob (red/off-white/red/red),
A10-Cara (blue/blue/blue/blue), A10-Dan (green/red/green/green).
Stub baseline at start: `$S/stub_requests.log` had **134** lines.

**Every CharlesBot verdict below came from `$S/stub_openrouter.py`, not a real

## PRIORITY FINDING: the "one game blocks everyone" worry is FALSE — but the admin's queue view is still global

**Verdict (of the concern):** NOT A BUG at the drain; a real UX problem in the queue view.

`backend/shot_auto_actions.py:process_queue_head(game_id)` asks
`AdminInterface().get_queue_head(game_id)`, and that query
(`backend/admin_interface.py:212-237`) filters `filter_by(game_id=game_id,
checked=False)`. The drain's "head of the queue" is therefore **the head of
*that game's* queue**, not of the global list.

Proved empirically, not just read:

* Global queue at the time: 36 unchecked shots, head
  `a43b443a-02f8-4456-ab4e-45fef0344ddf`, `game_id
  d2f1e030-c942-4e88-bd3f-6ac2dcdc1cd4` (another agent's game), `checked:false`,
  `ai_review_state: null` — i.e. an unreviewable, undecidable head sitting in
  front of everything.
* I switched review + auto-actions on **for my game only**, fired one shot, and
  the stub returned a confident hit matching A10-Bob's outfit.
* My shot `202d3b4c-dd73-4560-901c-20538a26b009` came back `checked: true`,
  `target_user_id = 1f62aa87-…` (A10-Bob) — auto-resolved, with the other game's
  ancient head still at position 0 of the global list afterwards.

So on the night a stuck shot in one game does **not** stop auto-adjudication in
another.

### Finding: the admin shot queue is global while every CharlesBot toggle is per-game
**Severity:** major (for a multi-game night), minor if only one game is ever live
**What happens:** `GET /api/admin_get_shots_info` takes no game id
(`backend/main.py:527`, `admin_interface.py:968-975`) and returns every unchecked
shot in the database, oldest first. The four toggles it is read next to
(`ai_shot_review_enabled`, `ai_auto_actions_enabled`, `ai_escalation_enabled`,
`ai_resolve_everything_enabled`) are all columns on `Game`. The result is a queue
page whose contents obey no toggle the admin can see on that page: shots from a
game with review off sit interleaved with annotated shots from a game with it on,
and there is no game column to tell them apart.
**How to reproduce:** open `/admin` → shot queue with more than one game in the DB.
36 shots were listed; 30-odd belonged to games I did not create.
**Where:** `backend/main.py:527`, `backend/admin_interface.py:968`
**Why it matters for the 19th:** if only one game exists on the night this is
invisible. If a test game or an aborted game is left in the DB, its shots
permanently occupy the top of the admin's list and every real shot is below
them — the admin scrolls past dead shots all night. Worth deleting stale games
before kickoff.

## Toggling ai_shot_review_enabled, ai_auto_actions_enabled, ai_escalation_enabled and ai_resolve_everything_enabled, and confirming each one actually changes queue behaviour (not just the toggle state)

**Verdict:** WORKS (all four gates observably change behaviour, not just state)
**Evidence:** `$S/shots/A10-admin-top.png` (the four checkboxes at 390x844, with
escalation ticked by default and the other three clear),
`$S/shots/A10-toggles-mygame.png`; stub call counts from `$S/stub_requests.log`.

Defaults confirmed on a freshly created game (`admin_list_games`):
`ai_shot_review_enabled:false`, `ai_auto_actions_enabled:false`,
`ai_escalation_enabled:**true**`, `ai_resolve_everything_enabled:false` — exactly
the documented "kill switch inside an opt-in" shape.

### `ai_shot_review_enabled` — annotates only

Driven by clicking the real checkbox in `/admin`, not by the API.

| step | observed |
| --- | --- |
| toggle OFF, fire shot `85188660-…` | **0** stub requests; `ai_review_state: null` |
| toggle ON in the UI | **2** stub requests, both `model: stub/vision-flash`; state `done`, outcome `hit_player` |
| immediately after | `checked: false`, `target_user_id: null` |

So switching review on both (a) picked up the shot that had arrived while it was
off — the backlog path in `admin_interface.py:460-503` — and (b) left the shot in
the queue. Annotation only, as specified.

(Each single review is **two** stub requests, not one: the screened-zoom
follow-up turn. Worth knowing before anyone estimates the API bill — the
per-shot cost is one prompt plus one zoom turn.)

### `ai_auto_actions_enabled` — resolves the head

With the review already stored and auto-actions off, the shot sat unresolved.
Ticking the auto-actions box in the UI resolved it **with zero further stub
calls**: `checked: true`, `target_user_id = 1f62aa87-…` (A10-Bob, whose outfit
the stub's fabricated reading matched). That is `admin_set_ai_auto_actions`
calling `process_queue_head` on enable (`backend/main.py:641-652`) acting on the
stored annotation.

Head-only ordering is checked separately below.

### `ai_escalation_enabled` — the kill switch, and it really does gate the second model

Setup: review ON, auto-actions ON, resolve-everything OFF. Stub steered to read
tshirt/trousers/hat confidently and leave **armbands** unread — the documented
"3 readable channels without armbands" rung.

| escalation | observed |
| --- | --- |
| **OFF** (unticked in the UI) | shot `a40800d7-…`: 2 `stub/vision-flash` calls, review `done`, outcome `hit_player`, `ai_escalation_state: null`, `checked: false` — no second model called at all, shot handed to the admin |
| **ON** (ticked in the UI) | exactly **1** further call, `model: stub/vision-pro`; `ai_escalation_state: done` |

The pro model is a *different* model id in the request log, so this is proof and
not inference. The stub's escalated reply named a candidate that was not on the
list, and the backend correctly downgraded it to
`{"verdict":"unsure", …, "[named candidate '', who is not on the candidate list,
so treated as unsure]"}` — an "unsure" escalation left the shot `checked: false`
with the admin, as specified.

### Head-of-queue blocking, within one game — confirmed

While `a40800d7-…` sat undecidable at the head of **my game's** queue, I fired a
second shot `8a39f23a-…` whose stub reading was a perfect, 0.95-confidence,
four-channel match for A10-Cara. It was reviewed (`done`, `hit_player`) and
**not** resolved: `checked: false`, `target_user_id: null`. It stayed blocked
across the escalation as well. That is the specified ordering working.

### `classify()`'s retired bystander mapping — confirmed retired

The "too few readable channels" reading above came back `outcome: "hit_player"`,
never `hit_bystander`. Unreadable garments no longer manufacture a bystander
verdict on their own.

### `ai_resolve_everything_enabled` — relaxes the confidence gate and nothing else

Positive case: my game's queue was stuck with `a40800d7-…` (escalated, verdict
`unsure`) at the head and `8a39f23a-…` (confident hit on A10-Cara) blocked behind
it. Ticking **"CharlesBot resolves every shot it can"** in the UI resolved
**both, with zero further stub calls**: `a40800d7` → A10-Bob (the weak reading's
own best ranking, `_forced_fallback`), then `8a39f23a` → A10-Cara. So the toggle
relaxed the accuracy bar and the *strict ordering was preserved* — the head went
first and the one behind it followed.

Negative cases, both with resolve-everything **on** and auto-actions **on**:

| case | shot | result |
| --- | --- | --- |
| reading that fits nobody (`inconsistent: true` — stub read yellow/mustard/yellow/yellow, an outfit no player wears) | `aeb5fc6a-…` | head of the queue, `checked: false` — **not** force-resolved, and correctly not escalated either (4 channels read = auto rung) |
| review that errored (`state: "error"`, "vision call failed after 3 attempts: OpenRouter returned 500") | `6978980e-…` | head of the queue after I cleared the one in front, `checked: false` — **not** force-resolved |

Both are exactly the "never forced, because there would be nothing to appeal"
carve-outs in `shot_auto_actions._target_from_ranking` / `_decide`. The UI
surfaces the reason honestly: two amber notes on the candidate panel, *"Two
candidates are too close to call"* and *"The reading fits nobody cleanly"*
(`$S/shots/A10-queue-shotE-escalated.png`).

## Not re-reviewing an already-reviewed shot when the AI toggle is switched on and off again

**Verdict:** WORKS
**Evidence:** stub request-log deltas, `$S/stub_requests.log`.

* Shot `85188660-…` reviewed once (2 `stub/vision-flash` requests), state `done`.
* Unticked "CharlesBot reviews shot photos automatically" in the UI, ticked it
  again, waited 4 s: **0 new stub requests.**
* The complementary half also works: a shot fired while the toggle was **off**
  (`85188660-…` itself, 0 calls at fire time, `ai_review_state: null`) *was*
  picked up and reviewed the moment the toggle went back on — the backlog query
  in `backend/admin_interface.py:483-497` selecting `ai_review_state IS NULL OR
  = 'error'`.

So off→on is idempotent for a done review and catch-up for a new one. Nothing to
report beyond the verdict.

### Finding: "Run escalated review" reports its one foreseeable failure as a raw browser alert()
**Severity:** minor
**What happens:** on a shot with no completed review the button pops a native
`alert()`. Everything else on this page reports state in the page itself (the red
"CharlesBot review failed" banner, the amber "Needs your call" pill). A modal
alert is also the one thing that cannot be dismissed one-handed without aiming.
**How to reproduce:** open a shot whose `ai_review_state` is `error` or null in
`/admin/shots`, press "Run escalated review".
**Where:** `react-ui/src/ShotQueue.js:827-829` (button) → `escalateShot()`;
guard at `backend/main.py:722-730`.
**Why it matters for the 19th:** low. It is the correct refusal, just shouted. But
the recovery ("Re-run CharlesBot review" first) is one button to the left and the
alert does not say to press it in those words.

### Finding: on a 390px phone the queue's error banner overflows off-screen, and the Hit buttons sit on top of the player names
**Severity:** minor (cosmetic-plus: one of them hides information the admin needs)
**What happens:** two things in `$S/shots/A10-queue-shotF-escalate-alert.png`:

**Where:** `react-ui/src/ShotQueue.js` + `ShotQueue.module.css` — the page is a

**Why it matters for the 19th:** the shot queue is the admin's main screen and
the brief says the game is driven one-handed on a phone. Wrong-name taps are the

## Other things found on the way

### Finding: one unrenderable shot image 500s `admin_get_shot` and floods the queue page with uncaught errors
**Severity:** major
**What happens:** `GET /api/admin_get_shot?shot_id=06e89772-…` returns **500**.
Backend traceback:
`backend/main.py:564 admin_get_shot` → `admin_interface.py:942 markup_shot_model`
→ `image_processing.py:254 draw_cross_on_image` → PIL
`TypeError: color must be int or single-element tuple`. The aim-cross is drawn in
an RGB colour onto an image that is not RGB (a greyscale/palette PNG), and
nothing catches it.

The queue page then makes it worse: `update()` in `ShotQueue.js:663-670` does
`Promise.all(shot_ids.map(getShotFromCache))` over **every** id from the global
`admin_get_shots_info`, and `fetchAndCache` throws on a non-ok response. Each bad
shot becomes an unhandled rejection — `Error fetching shot: Internal Server
Error` ×3 in `page.consoleErrors` — and in the CRA dev server the error overlay
covers the page and swallows every click, so the shot queue is unusable until the
overlay is dismissed. In a production build there is no overlay, so it degrades to
console noise plus one shot that never loads, but the underlying 500 is real
either way.
**How to reproduce:** have any shot in the DB whose photo is not an RGB image
(mine were RGB; shot `06e89772-…` is another agent's), then open `/admin/shots`.
**Where:** `backend/image_processing.py:254`, `backend/admin_interface.py:942`,
`react-ui/src/ShotQueue.js:663-670`.
**Why it matters for the 19th:** real phone cameras send RGB JPEGs, so the PIL
crash is unlikely to fire on the night — but the *frontend* half is not
conditional on that: any single shot whose fetch fails (500, timeout, a dropped
connection on a slow venue wifi) takes the whole preload down with an unhandled
rejection, on the admin's only adjudication screen, and the global queue means the
bad shot need not even belong to the game being run. Worth a `.catch` either way.

### Note: each CharlesBot review is two upstream requests, not one
The cheap pass fires **2** requests to the vision endpoint per shot (the screening
turn plus the zoom turn); the escalation fires **1**. Relevant only to cost
estimates.

### Note on trust
Every verdict quoted above — "hit on A10-Bob", "unsure", the 47%/47% ranking — was
fabricated by `$S/stub_openrouter.py` to my instruction. What is tested here is
**which gate admitted which verdict, and in what order**. Nothing here says a real
model would read a real photograph correctly, and the auto-action thresholds
(0.6 overall, the posterior, `ESCALATION_HIT_THRESHOLD`) have not been calibrated
against a single real image.
