Own game: `A5-Game` (`fb51b9c4-8e3e-4275-a0b1-ea89ee9c1a05`), teams `A5-Red` / `A5-Blue`,
players `A5-Wake`, `A5-Map`, `A5-Map2`, `A5-Map3`, `A5-Drop`, `A5-Ticker`, `A5-Joiner`,

## The screen staying awake during play (R3 — Screen Wake Lock), and that the phone's own lock button still turns the screen off on request.

**Verdict:** WORKS WITH CAVEATS (the "lock button" half is NOT TESTABLE HERE)

**Evidence:**
- Headless Chromium 141 *does* implement the Screen Wake Lock API, so this was tested for
  real, not just read. `"wakeLock" in navigator` is true and `isSecureContext` is true on
  `http://127.0.0.1:3000`. The request is rejected `NotAllowedError: Wake Lock permission
  request denied` unless the Playwright context is granted the `screen-wake-lock`
  permission; with it granted, `navigator.wakeLock.request("screen")` resolves to a live
  sentinel. Both cases were exercised.
- Method: an `addInitScript` shim wrapped the *real* `navigator.wakeLock`, logging every
  `request`/`release` and keeping the native sentinels, and shimmed `document.visibilityState`
  so a background/foreground could be simulated (see below for why that was necessary).
- Playing, permission granted (`$S/shots/a5_wake_playing.png` — normal game view over the
  fake camera): log is `request(granted), request(granted), release` — two requests and one
  release is React 18 StrictMode's double-invoked effect in the dev server, not a bug; one
  live sentinel remains held.
- Simulated background then foreground: no request while hidden, one fresh
  `request(granted)` on returning to visible. The re-acquisition path R3 was written for
  does fire.
- Denied case: every other run in this report used a context *without* the
  `screen-wake-lock` grant, so the request rejected each time. The game view rendered and
  played normally, no unhandled rejection, no console error — `useWakeLock.js:21`'s
  `.catch(() => {})` holds. A phone that refuses the lock (low battery) loses nothing.
- Not testable here, honestly: (a) whether the phone's own power button still turns the
  screen off — headless Chromium has no screen and no power button. Per spec a `"screen"`
  wake lock only suppresses the *idle* timer and cannot block a manual lock, and the code
  requests nothing else, so there is no mechanism by which this could break; but I did not
  observe it. (b) Real backgrounding: Chromium in this container reports
  `visibilityState: "visible"` for every page even when another tab is fronted, and
  `Emulation.setPageVisibilityState` no longer exists in this CDP build, so the auto-release
  the browser performs on hide could not be observed — only the app's re-acquire on the
  `visibilitychange` event.

### Finding: the wake lock is held on the onboarding screen, before the game starts
**Severity:** minor
**What happens:** `useWakeLock()` is called at the top of `GetView`, above the early return
that shows `OnboardingView`. A player who has opened the app but has not set a name — or
whose game is not active yet, or who has not granted camera/location — is already holding a
screen lock. Verified: the "enter your name" screen (`$S/shots/a5_wake_onboarding.png`) logged
`request(granted)` with no name set and no team.
**How to reproduce:** open `/` with a fresh cookie jar and a context granted
`screen-wake-lock`; the log records a granted request while the name prompt is on screen.
**Where:** `react-ui/src/UserMode.js:30` (hook) vs the `OnboardingView` return at
`react-ui/src/UserMode.js:68`.
**Why it matters for the 19th:** players will have the app open in the pub well before the
game goes active. Their screens will not sleep for that whole time, on the single biggest
battery draw in the game, and R3 shipped deliberately without a toggle to turn it off.

### Finding: the lock is still held after the player dies, and re-acquired on every return to foreground
**Severity:** minor
**What happens:** killing the player (`admin_set_hp?num=0`) leaves the lock held — the hook
is unconditional, and a subsequent `visibilitychange` while dead re-requests it
(verified in the log). A dead player's phone stays awake until they close the tab.
`$S/shots/a5_wake_dead_view.png` shows the YOU DIED view, map and ticker still live.
**Where:** `react-ui/src/useWakeLock.js:7-35`, mounted at `react-ui/src/UserMode.js:30`.
**Why it matters for the 19th:** the first players out are the ones with the longest wait
and the most to lose from a flat battery; they are also the ones who no longer need the
screen. Arguably intended ("mounted unconditionally" in the roadmap), so flagging as a
decision to confirm rather than a defect.

### Finding: a re-acquired sentinel replaces the old one without releasing it
**Severity:** cosmetic (benign on a real phone)
**What happens:** `acquire()` overwrites `sentinel` with the new lock. On a real device the
old one has already been auto-released by the browser when the page was hidden, so nothing
leaks; in this container, where the page never truly hides, the previously held native
sentinel stayed unreleased after re-acquisition (observed: 2 unreleased sentinels).
**Where:** `react-ui/src/useWakeLock.js:15-21`.
**Why it matters for the 19th:** it doesn't, on a phone. Noted only so nobody re-discovers
it as a "leak" when reading the hook.

## The map view, including drop/circle locations on the live Westminster venue map (#12).

**Verdict:** WORKS WITH CAVEATS

**Evidence:**
- The active venue is Westminster (`backend/venues.py:ACTIVE_VENUE`), and
  `/api/get_venue` returns it. The player's map loads
  `static/media/map_westminster.*.jpg` — the correct image
  (`$S/shots/a5_map_main_view.png`, `$S/shots/a5_popped_all_circles.png`: hand-drawn
  Westminster with all ten pubs, Big Ben, the Abbey, Millbank).
- Georeferencing is right. Corner mini-map clips at four fixed positions
  (`$S/shots/a5_corner_house.png`, `a5_corner_bigben.png`, `a5_corner_warwick.png`,
  `a5_corner_offmap.png`): at House Absolute the helmet dot sits on the House Absolute
  icon; moved to Big Ben's coordinates the dot lands on the Big Ben tower; moved to The
  Warwick's coordinates it lands on "The Warwick". The dot always renders at the box centre
  by design and the *background* shifts (`backgroundPosition` went
  `-330,-330` → `-592,-652` → `+35,-100` px), which is the corner map following the player.
- Off the map (51.52, -0.10, ~2.5 km NE of the crop) is handled sanely: the mini-map goes
  blank white with the dot still centred, no NaN, no crash, no console error
  (`$S/shots/a5_corner_offmap.png`).
- All three circles render and are distinguishable (`$S/shots/a5_popped_all_circles.png`):
  exclusion as a clear disc with everything outside it washed dark red, next as a red
  dotted pulsing ring (drawn at Big Ben, then at The Royal Oak), drop as a blue ring.
- Live SSE, no reload: with a `window.__loadMarker` set at page load and checked after each
  change, setting a NEXT circle and clearing DROP and EXCLUSION all changed the map (and the
  ticker) with the marker unchanged — `next` element count 1→0 on clear, `drop` 1→0,
  `excl` 1→0 (`$S/shots/a5_clear_exclusion.png`).
- The corner-map clipping reported in the earlier smoke test: **refuted as an overflow bug,
  confirmed as a zero-margin layout.** `document.documentElement.scrollWidth === innerWidth
  === 390` in every state, and the mini-map's box measures left 270 / right 390 / top 0 —
  exactly flush with the viewport, nothing off-screen. What is lost is its drop shadow and
  the breathing room on the top and right; see the finding below.

### Finding: `admin_clear_circle` announces the circle as if it had just been set
**Severity:** major (for game night)
**What happens:** clearing a circle removes it from the map (correct) *and* posts the
"appeared" ticker line to every player. Observed verbatim: clearing DROP put "A supply drop
has appeared! It's marked in blue" on the ticker at the same instant the drop circle vanished
from the map; clearing EXCLUSION posted "The circle has changed - if you're outside, get
moving!". Clearing NEXT posts "The next circle has been announced! Check the map...".
**How to reproduce:** `POST /api/admin_clear_circle?game_id=<g>&name=DROP` with a player's
map open; the drop disappears and the ticker announces a drop.
**Where:** `backend/main.py:990-1000` (`admin_clear_circle` calls `set_circles` with
lat/long/radius `None`) → `backend/admin_interface.py:306-350`, which always
`tk.send_ticker_message(message_type, ...)` regardless of whether it set or cleared.
**Why it matters for the 19th:** a whole team runs to a supply drop that the admin just
removed, or is told the circle changed when it was switched off. The admin cannot clear a
circle quietly. (Note also that `main.py` defines two functions both literally named
`admin_set_circle` — line 951 and line 991 — the second shadowing the first. Harmless,
since the decorator registers by path, but it makes the clear endpoint hard to grep for.)

### Finding: the drop circle is invisible for ~70% of its animation and never shows its real radius
**Severity:** minor
**What happens:** `.dropCircle` runs a 2 s `zoom` keyframe: scale 0.1 → 5.0 while the border
fades to fully transparent by 30%, then stays transparent and 5x-scaled for the remaining
1.4 s. Burst screenshots 180 ms apart at the drop location (`$S/shots/a5_drop_0.png` shows a
big blue ring, `$S/shots/a5_drop_3.png` shows nothing at all at the same place) confirm the
ring is on screen for well under a second in every two, and that the ring you *do* see is up
to five times the true radius (a 50 m drop drew a ring covering several streets).
**Where:** `react-ui/src/MapView.module.css:97-120`.
**Why it matters for the 19th:** a player glancing at the corner map for a second may see
nothing where a drop is, and if they do see it they cannot tell how big the drop area is. It
reads as a radar ping rather than a zone; if that is the intent it is fine, but the exclusion
and next circles both show their true size and this one does not.

### Finding: the popped-out map wastes more than half the panel on blank white
**Severity:** cosmetic
**What happens:** the popped-out map is 80vw x 80vh (312 x 675 px at 390x844), but the map
image is fitted to the *width*, so it is drawn 312 x 312 with ~180 px of empty white above
and below. Visible in `$S/shots/a5_clear_exclusion.png` and
`$S/shots/a5_popped_all_circles.png`. When an exclusion circle is set, that blank margin is
tinted red too, which makes the panel look like map you cannot reach.
**Where:** `react-ui/src/MapView.js:265-268` — `box_width_km = max(MAP_WIDTH_KM,
MAP_HEIGHT_KM * aspect)`, i.e. fit-to-width, against a square 1.3 x 1.3 km Westminster crop
in a portrait box.
**Why it matters for the 19th:** the map is the thing players squint at in the dark; it is
currently drawn at 46% of the space the pop-out already takes. It is pinch-zoomable, so this
is a default, not a wall.

### Finding: the corner mini-map is flush against the top and right edges of the screen
**Severity:** cosmetic
**What happens:** the mini-map's box sits at left 270 / right 390 / top 0 in a 390-wide
viewport — no margin at all, so its `box-shadow` (`0 0 0.2em 0.2em`) is cut on those two
sides. Nothing overflows and no map content is lost (`scrollWidth === innerWidth`).
**Where:** `react-ui/src/UserMode.module.css:1-8` (`monitorsContainer`,
`justify-content: space-between`, no padding) with `react-ui/src/MapView.module.css:19-22`
(`10em` square, fixed 120 px because `index.css` sets `* { font-size: 12px }`).
**Why it matters for the 19th:** on a notched phone in fullscreen the top-right corner of the
map will sit under the status bar / rounded display corner. This is what the earlier smoke
test saw; it is a margin problem, not a clipping bug.

### Finding: outside the exclusion circle, the corner map is a featureless red square
**Severity:** question
**What happens:** the exclusion overlay is a 10000 px box-shadow, so once the player is more
than ~100 m outside the circle the entire 0.2 km-wide corner map is tinted with no boundary
visible and no direction cue (`$S/shots/a5_corner_bigben.png`, `a5_corner_warwick.png` — the
map is legible through the tint, but the circle edge is nowhere on it). The player has to
pop the map out to find out which way to run.
**Where:** `react-ui/src/MapView.module.css:58-64` plus the 0.2 km corner window
(`corner_width_km` in `backend/venues.py`).
**Why it matters for the 19th:** "get moving" is exactly the moment the corner map is
supposed to answer a question, and it is the moment it stops being able to. Raised as a
question because the pop-out does answer it and this may be an accepted trade.

## The ticker feed for game announcements.

**Verdict:** WORKS

**Evidence:**
- Live over SSE with no reload: a `window.__loadMarker` set at page load was unchanged
  across every observation below. `admin_send_custom_ticker_message` reached the player's
  ticker in **~2.0 s** (polled at 200 ms).
- Ordering is newest-first and exactly three lines are shown (`num_messages = 3`,
  `react-ui/src/TickerView.js:21`): after sending ONE..FOUR in order, the ticker read FOUR /
  THREE / TWO (`$S/shots/a5_ticker_four.png`).
- Real events arrive the same way: `A5-Joiner has joined team A5-Blue` appeared when a new
  player was added to a team, `You were given 1x ammo!` on `admin_give_ammo`, `Admin killed
  A5-Dead!` on a kill, and the circle announcements above. Private lines render italic
  (class `user`), public ones upright (`$S/shots/a5_ticker_events.png`) — the distinction
  is visible.
- Long messages wrap rather than overflow: a 178-character message wrapped to four
  right-aligned lines, left edge at x=83, still inside the viewport, and pushed the older
  lines down without colliding with the mini-map above it
  (`$S/shots/a5_ticker_long_clip.png`). `scrollWidth` stayed at 390 throughout.
- Legibility over the camera: white text with a 2 px black `text-shadow` and no scrim. Over
  the fake camera's mid-green it is comfortably readable in every screenshot. I cannot test
  it against a real bright sky or a white wall here — that is the case worth eyeballing on a
  real phone before the 19th, since there is no backing plate behind the text.

### Finding: ticker text is locked to 12px regardless of the phone's text-size setting
**Severity:** minor
**What happens:** `react-ui/src/index.css:14-17` sets `* { font-size: 12px }`, so every
ticker line (and the whole UI) renders at 12 px CSS on every device and ignores the player's
own accessibility text-size setting. Measured line boxes are 18 px tall.
**Where:** `react-ui/src/index.css:14-17`.
**Why it matters for the 19th:** the ticker is how "the circle has changed" reaches a player,
read at arm's length, at night, while walking. 12 px is small for that, and a player who has
turned their phone's text up gets nothing.

### Finding: geolocation watch errors spam the console when the fix changes
**Severity:** question (likely a container artefact)
**What happens:** `Error watching position: GeolocationPositionError` is logged repeatedly
whenever the Playwright fake GPS is moved, from `MapView.js`'s `watchPosition` error handler.
The map still updates correctly on the next good fix, and nothing user-visible breaks.
**Why it matters for the 19th:** I believe this is the headless fake-geolocation provider,
not the app — but the same handler only `console.error`s, so on a real phone a GPS dropout is
silent to the player and their dot simply stops moving. Worth knowing when someone says "the
map froze".
