## The admin nav (finger-sized button row) on a real phone screen, not just a desktop browser.

**Verdict:** WORKS WITH CAVEATS
**Evidence:** `$S/shots/A12-nav_admin.png`, `A12-nav_admin_shots.png`,
`A12-nav_admin_replay.png`, `A12-nav_admin_reference.png`,
`A12-nav_admin_identity.png`, `A12-nav_admin_identity-overrides.png`,
`A12-nav_admin_login.png`, `A12-nav_test.png`,
`A12-reference-scrolled-right.png`.

The nav itself behaves: on all seven admin routes it wraps to three rows
(3 / 2 / 3) inside 390px, never scrolls sideways, and the active page is a
solid blue pill that is legible at arm's length. Every admin route in
`react-ui/src/index.js` (`/admin`, `/admin/shots`, `/admin/replay`,
`/admin/reference`, `/admin/identity`, `/admin/identity-overrides`,
`/admin/login`) is in the nav — no orphaned admin pages — and every page
therefore has a way back. `/test` has no nav, but it is a dev scratch page,
not an admin one. The nav costs 126px of an 844px screen (15%) on every page
and scrolls away with the content, which is the right trade.

### Finding: every nav button is 36px tall, not the ">44px" the CSS says
**Severity:** minor
**What happens:** `AdminCommon.module.css` sizes nav links `min-height: 3em`
with the comment "Comfortably above the ~44px minimum touch target". It is not:
`react-ui/src/index.css` line 14-17 sets `* { font-size: 12px }` for the whole
app, so 1em = 12px and 3em = **36px**. Measured with `getBoundingClientRect()`
on all eight links on all seven admin pages: height 36px, widths 107-187px.
That is 18% under the iOS 44pt / Android 48dp minimum.
The same 12px basis shrinks the rest of the house style: on
`/admin/reference` the exemplar's `3.5em` primary button and `3em` button row
come out at 42px and 36px; only the roster row (`3.2em` plus padding, measured
50px) actually clears 44. Elsewhere it is worse — on `/admin/shots` the
Missed / Bystander / Refund / Hit adjudication buttons measure **24px** tall
and the queue/contested radios **13px**; on `/admin/replay` the buttons are
24px and the two `<select>`s 18px.
**How to reproduce:** load any admin page at 390x844 and measure
`document.querySelector("nav a").getBoundingClientRect().height` → 36.
**Where:** `react-ui/src/index.css:14-17` (`* { font-size: 12px }`),
`react-ui/src/AdminCommon.module.css:13-14`.
**Why it matters for the 19th:** the whole point of the button row is one-handed
use with a box of wristbands in the other hand. Every `em`-based target in the
admin UI is silently 25% smaller than the author intended, and the miss-rate
cost lands on the buttons that adjudicate shots. Note this is a *policy*
mismatch, not a rendering artefact of the container: the numbers are CSS pixels
at DPR 3, exactly what a phone gets.

### Finding: four of the seven admin pages scroll horizontally at 390px
**Severity:** major
**What happens:** `document.documentElement.scrollWidth` at a 390px viewport:
`/admin/reference` **778px**, `/admin/identity-overrides` **778px**,
`/admin/identity` 610px, `/admin` 408px, `/admin/shots` 401px
(`/admin/replay` and `/admin/login` are clean at 390px).
The two 778px pages are the same cause: the `GameSelector` `<select>` renders
its longest option (`a47c0fcf (Red Team, Blue Team, Green Team, Yellow Team,
Purple Team, Orange Team, Pink Team, Cyan Team, Brown Team, Black Team)`) with
no width cap, so a native select 769px wide doubles the page. Swipe right and
you get a blank white page with the tail of one dropdown and no nav at all —
see `A12-reference-scrolled-right.png` (scrollX 388). The sample game has ten
teams, which is exactly what a real game night looks like.
The lesser offenders: `/admin/identity` is the scheme table (582px),
`/admin` the expanded MapView mini-map (408px), `/admin/shots` the
Queue / Contested / "Show adjudicated shots" labels (390px wide starting at
x=11).
**How to reproduce:** log in as admin at 390x844, go to `/admin/reference` with
a game that has several teams, swipe left-to-right.
**Where:** `react-ui/src/ReferencePhotos.js:376-396` and
`react-ui/src/AdminIdentity.js:657-677` — the same `GameSelector` component
copy-pasted into both files, neither with a `max-width`.
**Why it matters for the 19th:** the door kit-check page (`/admin/reference`) is
used standing up with a queue of players in front of you; a page that slides
sideways under your thumb and hides the nav is the wrong thing to be fighting.
The fix is one CSS line, and it is the same line in two places.

### Finding: "Player view" is a one-way trip

## The running app version shown on admin pages, and that it matches what is actually deployed.

**Verdict:** WORKS WITH CAVEATS
**Evidence:** `curl --noproxy '*' /api/get_version` → `{"version":"6cf5608"}`;
`git rev-parse --short HEAD` → `6cf5608` (tree clean). The footer
`version 6cf5608` is present at the bottom of all seven admin pages — visible in
every `A12-nav_admin*.png`. It matches.

Mechanics: `backend/main.py:133` prefers a `backend/VERSION` file (written at
build time by `versionOverlay` in `flake.nix`, which uses `self.shortRev` /
`self.dirtyShortRev` / `"unknown"`) and falls back to `git rev-parse --short
HEAD` in a checkout. This container has no `backend/VERSION`, so the git
fallback is what I exercised; a deployed droplet/LXC/Docker image takes the
baked file instead. `VERSION` is computed once at import, i.e. at process
start, which is correct for a deployment (a new rev means a new process).
`VersionFooter` fetches once per mount, and SPA navigation between admin pages
remounts it, so it only goes stale if you sit on one page across a redeploy.

### Finding: the footer identifies the backend only — nothing says which frontend you are looking at
**Severity:** minor
**What happens:** `get_version` is consumed in exactly one place
(`react-ui/src/AdminCommon.js:193`) and reports the backend's git rev. The
React bundle carries no version of its own. Backend and frontend are separate
artefacts in every deployment target (`dockerFrontend` / `dockerBackend`,
the Express server in `server/`), and a browser can be holding a cached bundle
in any case, so "version 6cf5608" in the footer is not evidence that the JS
drawing that footer is 6cf5608.
**Why it matters for the 19th:** the footer exists so a screenshot of a problem
says which code produced it. For a frontend bug — which is most of what a
screenshot shows — it currently does not.

### Finding: the git fallback hides a dirty tree
**Severity:** minor
**What happens:** `_current_version`'s fallback runs `git rev-parse --short
HEAD` with no `--dirty`, so a checkout with uncommitted edits reports the last
commit's hash as though it were clean. The Nix path is careful about exactly
this (`dirtyShortRev`), so the two disagree about the same situation.
**How to reproduce:** edit any tracked file in a dev checkout, restart the
backend, `GET /api/get_version` — unchanged hash.
**Where:** `backend/main.py:144-150`.
**Why it matters for the 19th:** if anything is hot-fixed on the box on the
night, the version string will lie about it.

### Finding: the version is invisible to players, and to a logged-out admin
**Severity:** question
**What happens:** the footer is inside `AdminPage`'s authenticated branch, so
it does not render on the login form, and no player-facing page shows a version
at all. A player reporting "it did X on my phone" cannot say which build.
**Where:** `react-ui/src/AdminCommon.js:189-206, 210-245`.
**Why it matters for the 19th:** it is the players' screenshots you will be
triaging at 11pm, not the admin's. Worth deciding deliberately rather than by
omission.

## The replay workbench at /admin/replay (R1) — trialling a prompt/zoom/schema change against real shots without it touching stored data.

**Verdict:** WORKS
**Evidence:** `$S/shots/A12-replay-load.png`, `A12-replay-screened.png`,
`A12-replay-upfront.png`, `A12-replay-single.png`,
`A12-replay-screened-zoomed.png`, `A12-replay-effort-high.png`,
`A12-replay-stub-failing.png`, `A12-replay-custom-contract.png`,
`A12-replay-custom-transcript.png`; request log `$S/stub_requests.log`;
before/after review dumps `$S/a12/before.json`, `$S/a12/after.json`.

**The three parts of the contract genuinely travel together.** Changing
`zoom_mode` in the UI changes the number *and* the shape of the turns actually
sent (counted from `n_messages` in the stub log, one line per HTTP call):

| Conversation shape | HTTP calls | `n_messages` per call | transcript turns shown | zoom tag |
| --- | --- | --- | --- | --- |
| Screened zoom (live pipeline), no zoom wanted | 2 | 1, 3 | 4 | none |
| Screened zoom, stub asks for the zoom both times | 3 | 1, 3, 5 | 6 | "Zoomed in ×2" |
| Both views up front | 1 | 2 | 3 | "Zoomed in ×1" |
| One turn, no zoom | 1 | 1 | 2 | none |

The prompt reseeds with the shape (5186 / 5113 / 4744 characters for
screened / upfront / single), an *edited* prompt survives a shape change
un-clobbered (checked across two consecutive changes), and "Reset to live
contract" restores both boxes (schema back to its 3493-character default). The
schema box is editable independently and a bad edit is caught client-side:
`{not json` produces "The response schema is not valid JSON: Expected property
name or '}'…" and fires no request. A deliberately foreign schema
(`{hat_colour, sure}`) with a custom prompt in "one turn" mode came back
through the raw-reply path — "The reply did not match the standard reading:
'shot_hit_a_person' must be true or false; got None" plus the reply
pretty-printed — and the transcript confirms my prompt is what was sent
(`A12-replay-custom-transcript.png`). This is R1's bug demonstrably fixed.

**A replay stores nothing.** `admin_get_shot_ai_review` for my shot returned
`{"state":null,"review":null,"identification":null,"escalation_state":null,"escalation":null}`
both before and after nine replays across every shape, and `admin_get_shot`
was byte-identical before and after (`checked:false`, `result:null`); the nav's
queue badge stayed "Shot queue (2)". Vision images and zoom crops render
correctly (`A12-replay-screened-zoomed.png` shows the full frame plus Zoom 1
and Zoom 2, each with its own aim cross).

**The reasoning-effort override reaches the wire:** selecting "high" logged
`"reasoning": {"effort": "high"}` on the outgoing request; "Pipeline default"
logs `null`.

**Failures are reported, not swallowed:** with the stub set to `fail: true` the
card showed a red "Replay failed: 502: …vision call failed after 3 attempts:
OpenRouter returned 500…" after ~3s (three retries), the Replay button
re-enabled itself, and nothing hung.

### Finding: in "screened" mode the schema box does not apply to turn 1, and the follow-up wording is fixed
**Severity:** question
**What happens:** with a custom prompt and the default (screened) shape, the
transcript shows the model asked my prompt but forced into the pipeline's own
screening schema (`{"person_fills_less_than_half": false}`), then a fixed
second user turn the workbench cannot edit: *"The person fills at least half of
the screen… Now answer in full with the JSON described above."* Only the final
turn uses the schema in the box. This is arguably correct — "screened" is
defined as the live shape, and R1's answer is to pick `single` or `upfront`
when you are trialling a different question — but the page says the reply is
"forced into" the schema you typed, and for two of the up-to-three turns it is
not. Nothing in the UI hints at it; you find out by opening the transcript.
**How to reproduce:** `/admin/replay`, leave the shape on "Screened zoom (live
pipeline)", replace the prompt, replay, open "Full model transcript".
**Where:** `backend/shot_vision.py:945` and `:980` (`build_screening_schema()` on the
first call) and the `ZOOM_FOLLOW_UP` / `FULL_READING_REQUEST` constants around
`backend/shot_vision.py:430-457`.
**Why it matters for the 19th:** the roadmap's own warning is that a prompt
edited alone is a prompt overruled. The remaining hard-coded turns are a
smaller version of the same trap, and worth one sentence of UI copy rather than
a code change.

### Finding: the replay error text is a double-escaped JSON blob
**Severity:** cosmetic
**What happens:** the card shows
`Replay failed: 502: {"detail":"Replay failed: vision call failed after 3
attempts: OpenRouter returned 500: {\"error\": {\"message\": \"stub configured
to fail\"}}"}` — the status line, the FastAPI envelope and the provider's JSON,
nested. Readable, but on a 390px screen it is four wrapped lines of punctuation.
**Where:** `react-ui/src/ShotReplay.js` (`status: "error"`, `${response.status}:
${await response.text()}`).
